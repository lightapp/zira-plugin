# Band saw board inspection: how a site is rolled out

Shared by setup-bandsaw-site, validate-bandsaw-site, check-bandsaw-model and project-kamps-bandsaw-rollout. It records how the Kamps band saw rollout (hub agent-tools #62, from 2026-11-10) actually ran, so another person can run a site from chat. Values that change (master model, app build, test sets) live in the project skill's [fleet file](../skills/project-kamps-bandsaw-rollout/references/kamps-bandsaw-fleet.json); read it, and the hub issue when you can, before a site.

## What "board inspection" is
A band saw camera counts pallets at the count line (as before) and, at each pallet's first rest, takes one high-resolution still of the table (a "board still"). On the phone the board model (the **master**, one for every saw of the customer) finds every board, broken board and stringer, the pallet-state model says whether the pallet can be measured (measurable, broken_measurable, partially_dismantled, two_pallets_stacked, not_measurable, not_settled, operator_over, empty), and the app posts seven board fields with each still. A pallet size posts only when the boards agree (Vision-App 928 or later); board count and state post for every still. Stills upload to the data source's dataset folder `board-crops-YYYY-MM-DD` (the phone's local date).

## Roles
- **Hub (one session):** site order and status, the hub issue, starting one site session per site, the status bullets, and decisions. It never edits a site's cameras itself.
- **Site session (one per site):** the checklist for its saws, its test set and training candidates, its site report. It prepares customer material but never sends it.
- **Master-model owner (one session):** trains the next master from the sites' accepted stills, scores it on every site's test set, and pushes it to every rolled-out saw. Site sessions never train a model of their own.
- **Customer hub:** every email, report or request to the customer (site contacts, champions, management). Others hand it the PDF or text.
- **The person running the rollout** installs the app by MDM, approves every write and every paid job, and checks the flagged test stills. Hub-relayed approvals do not count for paid starts (label reviews, training): ask in the session that starts them.

## Approvals
Every production write is shown first as its exact preview and applied only after an explicit yes. A site's setup may be approved as **one batch**: list every write (each saw, each skill, each value), get one yes, then apply them one by one with the owning skill (configure-vision-camera, push-model, duplicate-dashboard, build-dataset, review-labels, compare-models), each once, and read each back. Anything not in the approved batch needs its own yes. Never retry a write whose outcome is unknown; read its state first.

## The site done criteria (Muli 2026-11-11, changed 2026-11-12)
Over a full shift, per saw:
- **Stills per pallet** (board stills ÷ counted pallets) 0.97–1.03, judged as shown (2 decimals). This is the counting check.
- **In readings:** at least 90 % of stills reach the readings (a Pallet State posted).
- **Size posted** for at least 70 % of measurable pallets (state measurable or broken_measurable).
- **48×40:** pallets shaped like 48×40 (long side 45–52 in, short 37–43 in) read a median length and width each within ±0.6 in of 48 × 40, judged as shown (1 decimal).
- **Counts** against the previous week's same window are shown for information only.
A saw passes when all four hold (pill **Pass**, otherwise **Held** naming the criterion). The site is **Ready** when every saw passes, otherwise **Held**, naming each saw and criterion. Add no other thresholds. A re-judge after a criteria change goes in the same report folder as `report-v2`.

## Shared definitions (every site computes the same; validate-bandsaw-site implements them)
- **Pallets:** sum of Units in the window. **Stills:** board stills taken in the window (the day's `board-crops-` folder when the window is the whole production day).
- **Pallet mix:** each posted size goes to the nearest of 48×40, 48×42, 48×48, 42×42, 40×40, 48×45, 45×45, 47×32, 48×36, 44×44, 38×26, 36×36, 30×30 (within 4 in on both sides, either orientation), otherwise Other; sizes under 5 % fold into Other; at most 6 bars.
- **Counts baseline (information):** the same clock window on the previous week's Mon–Fri days on which the saw counted; normal when inside that min–max. If the counting setup changed during that week, use only days after the change; none means no baseline.
- **Model scores (board-first):** run the models at confidence 0.25 and NMS IoU 0.45 on held-out test stills; greedy same-class matching by IoU. **Boards found** = board F1 at IoU 0.5, **Tight fit** = board F1 at IoU 0.75, **Length error** = median |long side predicted − long side labelled| in px on the 1024 still over board pairs matched at IoU 0.5. Rank models boards first ("the boards define sizes"), then stringers; broken boards only break ties.

## Setup values
- **Band saw settings** (configure-vision-camera `set`): `BandsawMeasureCapture` true (board stills on), `BandsawMeasureCapturesPerHour` 0 (no cap), `BandsawMeasureDataset` "board-crops", `BandsawMeasureDeskew` true (straighten), `BandsawHighResRecording` false, `BandsawMeasurePreLabels` **false** for the first (test) stills. The inspection and pallet-state model slots appear only once board stills are on.
- **Remote Upload Settings** (Vision-App 935 or later; the 938 rollout build has it): add `"SettingsUploadRequestMs": "<current epoch ms>"` to the same settings spec as the change (configure-vision-camera accepts it), and repeat it after every settings change. The camera then replaces Zira's stored copy of its settings, so a later Sync Settings or a replacement phone keeps the change. Proof: Zira's device record then has `cv.settings.settingsUpload.source = "remote-request"` with the app version, and the new keys in its stored settings (rerun setup-bandsaw-site `baseline`); the camera's `SettingsUploadResult` is not in the retained topics a backup reads. On older builds a person presses Upload Settings on the phone's Sync screen.
- **Crops:** phones are usually mounted portrait (2160 × 3840). Use a full-width square crop (`x 0, width 1, height 0.5625`) whose top sits just above the table's far edge, fitted on the first real stills' pallet boxes (setup-bandsaw-site `crop`), not on raw clips: raw-clip medians put the far plate 20–25 raw px lower than the stills do. The app widens a still's crop by itself when a pallet overhangs it.
- **Scale with the pallet-height correction** (Muli: "this need to be done for all bandsaws moving forward"): a pallet sits above the table, so a Scale fitted to the table edges over-reads by ~5–10 %. Fit the Scale so pallets shaped like 48×40 read 48 × 40 (setup-bandsaw-site `scale`), once about an hour of measurable pallets has posted at one Scale. Use "most common board = 40 in" only as a cross-check (some sites run 48×40s with 46-in boards). The ruler on the table (Length = table side) is the table reference; the old fleet table sizes are hints only. A known-pallet run (calibrate-bandsaw-remotely) is the stronger check when the site can run one.
- **Per-axis Scale** (`BandsawStillScaleFactorX/Y`, Vision-App 933+): only from a full-shift fit, when one saw's long and short sides disagree by more than ~1.5 %, with the person's OK.

## Steps that need Zira in the browser (no plugin route yet)
Use the user's signed-in Zira (the host's browser tool; never sign in for them).
- **Board fields.** Data source ⋮ → Edit (URL `/forms/ID?mode=edit&applyingIds=7&fromTab=data&siteId=…&siteName=…`; a bare `/forms/ID?mode=edit` opens a different builder) → AI Data Source Builder (AI Assist; check its text box is really showing before typing, or the text lands in the description). **Untick "Replace current data source fields"** (it is ticked by default and has been seen re-ticking itself after the prompt is sent: check it right before Apply). Prompt, word for word: `The field labels must be exactly these words and nothing else: "Board Count", "Pallet Length", "Pallet Width", "Pallet State", "Measured Board Length", "Min Board Length", "Max Board Length". Types: Board Count is type number. Pallet State is type text. Pallet Length, Pallet Width, Measured Board Length, Min Board Length and Max Board Length are each type physical (a physical measurement field) with measurement Length and unit Inch. None required, no min/max limits, no default values, no validation rules.` Say "type physical": the builder maps only a draft type "physical" to a Length field in inches; a draft type "Length" falls back to Text, and saving then creates new text metrics instead of the shared ones (Baltimore and Jacksonville, 2026-11-12).
  - **Before Save:** the draft card's details say `Type: physical` for the five lengths; in the editor each shows `Length • Metric on save` (not `Text • Metric on save`) and its label reads "(Inch)"; the names are exact (it once made a field "Board Count (Number)"). Safer still, pin each field's metric before the first save (an empty Metric box means "Metric on save").
  - **Manual fix** for a field saved wrong: expand it → Type **Length** (it jumps to the generic "Length" metric in Feet, "Duplicate metric") → metric search → pick **"<field name> (global)"** → Unit of measure **Inch** → save. Board Count and Pallet State: pick "Board Count (global)" / "Pallet State (global)".
  - **Read back** with setup-bandsaw-site `baseline`: Board Count 56829, Pallet Length 59842, Pallet Width 60829, Pallet State 60830 (Text), Measured / Min / Max Board Length 60831 / 60832 / 60833, the lengths Length in Inch, no limits (`missingFields`, `wrongFields`, `fieldsWithLimits` all empty), and readings keep arriving whole.
- **First push into the pallet-state slot.** The camera does not list the empty slot (`empty_slot_unlisted`), so push-model stops. In Zira: data source → Models → the pallet-state model → **Push to device**; the dialog's slot defaults to "Counting model": pick **Pallet state (band saw)** and check "Currently in this slot: Empty" before PUSH. Wait for the dialog to finish "Asking the device which slots it has…" before clicking. Then read the slot back with push-model `list`.
- **Listing stills (names, times, pallet boxes).** On a my.zira.us data source page, in the page: `fetch('/api/datasets/images?dataSourceId=ID&datasetName=board-crops-YYYY-MM-DD&keysOnly=true&pageSize=1000')` lists the stills (names carry the phone's local time, `bandsaw_YYYYMMDD_HHMMSS_mmm`); `POST /api/datasets/image-urls` `{keys, dataSourceId}` (or `GET /api/datasets/image-url?imageKey=…`) gives short-lived links to `/images/*.jpg` and `/meta/*.json`. Fetch and summarise inside the page; never copy the signed links into chat or the shell. With zira-prod AWS access, a read-only `aws s3 sync s3://prod-vision-hub/companies/C/sites/S/data-sources/ID/datasets/board-crops-DATE/train/ DIR` gets the stills and their meta instead.

## Gotchas seen on real saws
- Cameras may answer model and settings commands minutes late (Milton Cam 57 ~5 min): a `pending` push is not a failure; rerun the same command to keep watching. A settings apply with `no_device` on an online phone: rerun once with `--seconds 12`–`30`.
- Two sessions writing at once share `~/.config/zira/action-receipts.json.lock` ("busy"): retry after a few seconds.
- Zira's stored settings copy is often stale (months old on 841 saws); trust the camera's settings-state reply.
- The MDM pushes one app version to at most 10 devices: plan app releases in batches of ≤10 saws; sites run different builds.
- Cellular-only saws upload ~150–200 MB of stills a day.
- A camera-moved flag in Zira's record can be stale: compare raw clips from different weeks before acting on it.
- An operator's standing pallet in the counting zone undercounts (GR Band Saw 2); flipped pallets re-stilled within seconds push stills per pallet above 1. Look at stills around counts with no still before changing count geometry, and replay any count-line change on recorded clips first.
- Readings datasets: match by data source IDs, not just site and date (a site may also have a trimsaw).
- macOS has no `timeout` command; zsh does not split `$var` in `for` loops.
