---
name: build-dashboard
description: Build or update a Zira dashboard, including company-level dashboards across sites, with native charts, KPIs, tables, filters, indicators, shortcuts, embedded/custom widgets and AI summary widgets grounded in real source metrics, then verify saved settings and results. Use for new dashboards or requested widget changes; use show-dashboards to find existing dashboards and duplicate-dashboard to copy one.
---

Use the [local MCP tools](../../references/local-mcp.md) for the packaged commands below. The command examples describe arguments; invoke the corresponding MCP tool instead of running them in a shell.

Read [authorized browsing](../../references/browsing.md) and [guided actions](../../references/actions.md). Run helpers relative to this skill directory with the same `--profile`. Author the widgets here in Codex or Claude; the web AI builder is optional, not the required last step.

Use `dashboard_widgets` for context/save and `dashboards` for create/copy/edit through the local MCP tools. They wrap the same guarded internal-API helpers. Use the UI for verification of supported widget families, not authoring. If a tool or backend admission is unavailable, retain the draft and report the specific gap instead of switching to browser editing.

1. **Understand the decision.** Reuse the site, sources and purpose supplied. Ask only for a missing decision that changes the result: what users need to learn or act on, comparison/baseline, time window, or denominator. Turn the request into questions, then a short widget plan (question → metric/formula → visual → expected check). Suggestions are starting points, never the limits of the dashboard. Prefer native widgets over embeds when native calculations can answer the question.
2. **Ground the plan.** Discover sources with `node ../../scripts/browse.mjs devices --company-id ID --site-id ID`. Inspect metrics and a bounded sample using readings-report's `sources --metrics`, `fetch` and `query` when necessary; don't guess metric IDs, units, enum values, weighting or missing-data meaning. Explain unavailable data before substituting an approximation. For an existing dashboard, run `node ../../scripts/dashboard-widgets.mjs context --company-id ID --site-id ID --dashboard-id ID --out CONTEXT.json` and preserve unrelated widgets and settings.
3. **Create the container when needed.** Preview `node ../../scripts/dashboards.mjs create --company-id ID --site-id ID --name "…" --description "…" --data-source-ids ID,ID --range last-7-days --interval hourly --profile prod`. Choose range and interval for the actual question (`help` lists options). On `nameTaken`, reuse the selected dashboard or choose a distinct name. Apply the reviewed creation with `--apply` when authorized. Share its `url`, then run `dashboard-widgets.mjs context` for the created ID. An empty container is not a completed dashboard.
4. **Author custom widgets.** Read [native settings and payloads](references/native-widgets.md), and [analysis patterns](references/analysis-patterns.md) for formulas, weighted data and trimsaw reports. Write a JSON spec outside the plugin directory, using the context's actual metrics. Design the layout as a readable narrative: summary, explanation, comparison and inspectable detail. Use shared filters only when they help. For `indicator` and `shortcuts`, read [native indicators and shortcuts](references/operational-widgets.md). For other non-analytical families, consult [other widget settings](references/other-widgets.md); do not claim the helper supports a family it does not yet implement.
5. **Preview, save, verify.** Run `node ../../scripts/dashboard-widgets.mjs save --company-id ID --site-id ID --dashboard-id ID --spec SPEC.json --profile prod`. It validates the whole batch and returns exact payloads, the proposed layouts, `revision` and `warnings`. A `first_series_categories` warning means a column/bar chart may drop categories, because it draws only those of its first visible series; reorder the series or plan the browser check. Explain what will change and any approximation. Reuse the user's explicit authorization; otherwise obtain approval for that concrete plan. Run the same command with `--apply --expected REVISION`. Creation precedes dependent filter widgets. The helper has no delete route. It checks scope, stale previews, receipts, and read-back; a partial/unknown attempt stops without replay. On authorization denial, report the blocked route and retain the draft; report the capability gap and keep the draft; never use a different credential source or browser editing to bypass it.
6. **Review the result, not just the response.** Open the returned dashboard URL in the host browser. Verify every widget renders, populated metrics have data, every expected category appears, categories/legends/units make sense, filters affect their intended widgets, and desktop/mobile layouts are readable. Compare key totals, shares, weighted means and at least one distribution with independent raw-reading queries for the **same site-time range and filters**. Check a zero/empty range and a narrower populated range. A saved configuration is not evidence of a correct chart. Repair only authorized widgets after a fresh context/preview; preserve existing series IDs and untouched settings. Report verified behavior and remaining gaps honestly.

**Layout saves.** Settings-only batches do not write the layout. When adding or moving widgets, the complete outgoing layout is checked before any writes and transient drag state is removed. If a saved responsive layout is invalid, use the layout-only `dashboards edit` preview with `copyLayout` or explicit rows to repair it, then refresh widget context; do not use the browser to repair it. Batch swaps are validated against final positions.

**Company-level dashboards (several sites).** These are the dashboards on the company channel's Dashboards tab: no site, one company, and data sources from any of its sites. Read [company-level dashboards](references/company-dashboards.md).
- **List** them with `browse.mjs dashboards --company-id ID`, leaving out `--site-id`.
- **Create** one with `dashboards.mjs create --company-id ID --company-level [--data-source-ids …]`. It starts Private.
- **Change** it with `context`, `save`, `edit`, `delete-widgets`, `delete`, `sharing` and `restore`, leaving out `--site-id`.
- **Widgets:** native charts can group several sites' saws. `embedded` reuses a chart from another dashboard of the company, and `custom` charts a chosen set of saws.
- Keep it Private until the user decides who sees it.

**Change an existing dashboard without the browser.** For renames, settings, moving or resizing any widget (camera, live-count and shortcut tiles included), retargeting filters, shortcuts, camera tiles (data source, rotation) and live-count tiles (data source, `primaryMetric`), or giving tablet and phone views a real layout, write an edit spec and run `node ../../scripts/dashboards.mjs edit --company-id ID --site-id ID --dashboard-id ID --spec EDIT.json --profile prod` (`help` shows the spec). The preview lists every object's exact before/after paths and a `revision`; apply with `--apply --expected REVISION`. Each changed object is saved once, the dashboard is read back, and any field that changed besides the intended ones is reported as a mismatch. `"copyLayout": {"from": "lg", "to": ["md","sm","xs"]}` derives the tablet/phone layouts from desktop (phones stack full width in reading order). Dashboard names are unique per site (Zira answers HTTP 409); the preview refuses a taken name. Day start and first day of week are **site** settings shared by every dashboard: use `dashboards.mjs site-settings --day-start 05:00 --first-day-of-week monday`. Writes marked `needsPlatform` (dashboard settings, site settings, shortcut/camera/live-count widgets, list-valued filter conditions) need Zira's plugin access update for these saves (https://github.com/lightapp/platform/pull/248); until then apply stops with `not_enabled` before writing anything, and `--skip-platform` applies the rest. Do not fall back to clicking through the web editor for these; report what is pending instead.

Use `dataResearch` for KPI, grouped KPI, KPI table, column, bar, pie and time series; `derivedMetrics` for row calculations and category bins; `customAgg` for formulas after grouping. `header`, `filter`, read-only `readings`, historical last-reading `indicator`, ordered `shortcuts`, and `embedded`/`custom` (type 19, company-level) are also supported. Indicator/shortcut create/update payloads need their corresponding backend admission; preview support alone does not prove production availability. For an AI summary/AI Insights request, read [AI summary settings and payload](references/ai-summary.md) and use `aiSummary`; it saves a question and explicit source-widget references, not a static answer. The answer sees KPI values only, not grouped charts or tables. Referenced draft analytics are saved before the summary. Production backend admission supports type 18; verify availability in other environments. Don't replace an unsupported statistic (for example weighted percentiles) with a similarly named but different metric. There is no arbitrary JavaScript/HTML widget injection or scheduled-report creation in this flow.

Deliver the dashboard link, the questions it answers, the chosen time basis, and the validation result. State if only the container/draft exists or the browser/data checks remain blocked. Schedule summaries only when requested, using schedule-ai-report.

**Remove widgets or a dashboard.** Only when the user asks for it by name. Preview with `node ../../scripts/dashboards.mjs delete-widgets --company-id ID --site-id ID --dashboard-id ID --widget-ids A,B --profile prod` (or `--widget-names "X","Y"`), or `dashboards.mjs delete …` for a whole dashboard. Show the user every widget that would go, what points at it (`referencedBy`; `--unlink` removes those links and the preview shows each change), any shortcut cards that open the dashboard (`linkedFrom`; refused without `--allow-linked`) and the warning that a delete cannot be undone: the backup is a record to rebuild from, and `restore` does not recreate. After the user approves that exact list, rerun with `--apply --expected REVISION --backup-dir DIR`, and report `done`, `failed`, `notTried` and the backup path. Never add `--unlink`, `--allow-linked`, `--allow-locked` or `--keep-layout` on your own. On `blocked: not_enabled` nothing was changed: deletes need Zira's plugin access update for dashboard deletes; give `handoff.pageUrl`.

**One change on many dashboards.** To make the same change on several sites' dashboards (rename or describe a widget on each, add a section that exists on one dashboard to the others, set a layout), write a plan and run `node ../../scripts/dashboards.mjs rollout --plan PLAN.json --profile prod`: `{"version":1,"label":"…","change":{"edit":{…}} or {"copySection":{"source":{companyId,siteId,dashboardId},"header":"…"}},"sites":[{companyId,siteId,dashboardId,deviceMapping?}]}`. The preview writes nothing and shows each dashboard's exact changes; one dashboard that cannot take the change refuses the whole plan unless it is listed under `skip`. Show the user the per-dashboard changes, save the preview to a file, and only after they confirm rerun with `--apply --expected PREVIEW.json --backup-dir DIR`. Each dashboard is backed up before its first write, saved once and read back; the run stops at the first dashboard that fails, and `done`, `failed` and `notTried` say where it stands. Never rerun a failed dashboard without checking it in Zira; `dashboards.mjs restore --backup FILE` previews setting one back. `dashboards.mjs sharing` reads whether dashboards are shared (private = not shared) from Zira's server, which is the value to trust over the editor's settings dialog. Details: `dashboards.mjs help`.
