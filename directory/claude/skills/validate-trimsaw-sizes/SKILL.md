---
name: validate-trimsaw-sizes
description: Check whether a Zira trimsaw camera's stop buckets, uncut boards and pre-cut lengths make sense over a chosen window, usually the production since the last calibration, and build an interactive report that explains the charts. Finds relabelled stop lines, explains a high uncut (No Cut) share, checks the camera's scale from uncut boards and shows incoming lengths against the cuts made. Scores how tightly cut boards sit on their sizes and compares two windows, such as old and new stops. Compares the camera's raw recordings to show whether its view moved, and checks that against the readings at the same times. Use for "validate Trimsaw 2's sizes after Friday's calibration", "why is uncut 31% on Trimsaw 2", "are the stop lines and pre-cut right", "did the new stops improve Trimsaw 1", "did the camera move" or "explain the trimsaw size charts". Use calibrate-trimsaw-stops for the calibration values and on-camera steps, readings-report for general charts, health-report for device health and show-dashboards for existing Zira dashboards.
---

Use the [local MCP tools](../../references/local-mcp.md) for the packaged commands below. The command examples describe arguments; invoke the corresponding MCP tool instead of running them in a shell.

Read [authorized browsing](../../references/browsing.md) (including "Asking the user to choose"), [reading the report](references/reading-the-report.md) and [handing over local pages](../../references/local-pages.md). Run `node scripts/trimsaw-sizes.mjs …` from this skill's directory with the same `--profile`. It reads Zira through the readings-report cache and writes only to this computer: the cache, a derived copy of the dataset and the HTML report, and for the camera view (step 4) raw recordings, snapshots and a local Python runtime. Nothing is written to Zira or the camera.

**Show, then work.** Share the data source's Zira link as soon as it is known, then fetch.

For a saved native **Zira dashboard**, use [Build a Trimsaw Dashboard](../build-trimsaw-dashboard/SKILL.md).
This skill produces the separate local diagnostic report and retains its deeper scale/relabel analysis.

1. **Data source.** Resolve company and site through authorized discovery, reusing supplied or saved scope. List candidates with `node ../readings-report/scripts/readings.mjs sources --company-id ID --site-id ID --metrics [--search NAME]`. A trimsaw source has Precut Length, Postcut Length, Target Length and No Cut. Ask the user to pick exactly one; when one matches the name they gave, say which one you are using.
2. **Window.** Ask when the stop lines or calibration last changed if the user has not said. Run `windows --company-id ID --site-id ID --device-id ID --from ISO [--to ISO]` over enough days to include that change (default: the last 7 days, with the site's offset). In plain words, show the latest production periods, the change points (`stray-labels-ended`: a calibration session or another device posting; `measured-shift`: a calibration edit or the camera moved; `new-label`: a stop added), the relabels and the `suggested` window with its boards. Ask the user to confirm it, take the whole latest production period or give their own times. Mixing calibrations makes every chart misleading, so keep the window after the last change; a few hundred boards or more is enough.
3. **Check.** Run `check --dataset ID --from LOCAL --to LOCAL` (site time, such as `2026-10-09T10:00`). Say which stops ran and where their cut boards peak, and name each relabel (merged into one stop by default; `--merge none` or explicit pairs like `44=45` override it). Explain the scale check in plain words. When `scale.suggest` is true, ask how to show pre-cut: rescaled by an exact factor the user knows from the camera's calibration (best), by the suggested factor (`auto`, an estimate within about 1%), or as Zira measured it (`none`). Never rescale without asking. If the calibration changed inside the window, use a piecewise factor such as `1.050,1.043@2026-10-09T11:40`. Give the size fit from `fit` in plain words: the share of cut boards within ±0.25 and ±0.5 of their size, the median offset and p10–p90 width per stop, the unmatched split and No Cut. When the user knows a stop's calibration value differs from its size (a 42 stop calibrated at 41.7), add `--calibration 42=41.7`; never guess one.
4. **Camera view.** When readings drift with the time of day or between days (the drift chart, `measured-shift` changes in `windows`), or the user asks whether the camera moved, compare the camera's raw recordings over the validation window: `scene --data-source-id ID --from DAY [--to DAY]` (site-local days). It lists the recordings in Zira (read-only), takes the first clip of each recording window, up to three a day, downloads them into a private cache and matches a median-of-frames snapshot of each to the first one on steady details. `--list` shows the choice without downloading; `--names A,B` picks clips; `--reference NAME` picks the one to compare with (normally the first after the last calibration). When the camera's applied stop positions (analysis px) and scale are known, pass `--stops '{"42":126.9,"40":131.6}' --in-per-px 0.367` for the shift at each stop in inches; otherwise shifts are in px. Before the first run, `scene-setup` says what it would install: ask once ("Set up the camera-view check on this computer? It downloads about 30-60 MB of Python packages.") and run `scene-setup --confirm` only after the user agrees. `large_download` gives the size; rerun with `--confirm` once the user agrees. Say `summary.sentence` and each recording's verdict in plain words: `view_moved` (the whole recorded view moved together; before saying the camera moved, compare each stop's readings in the same hours: only a shift of every stop by about the predicted amount, in the same direction, at those times supports a camera move and a mount check; readings that did not move, or swung in opposite directions, point elsewhere, so ask which sizes the site ran that day), `part_moved` (only part of the picture moved), `steady` (under 0.5 px) or `uncertain` (that recording could not be compared). On `raw_videos_unavailable`, ask the user to download two or more raw clips from the data source's Videos tab (RAW VIDEOS) and run `scene --files A.mp4,B.mp4`. See [reading the report](references/reading-the-report.md#camera-view-over-time).
5. **Report.** Run `report --dataset ID --from LOCAL --to LOCAL --factor none|auto|F [--merge …] [--scene SCENE.json] --serve`. It writes the derived dataset and the report, starts the readings-report helper and prints `liveUrl`, `savedUrl`, `numbers` and `neighbors`. Open `liveUrl` in the host's browser. In chat, give the main points from `numbers`, `scale`, `relabels` and the neighboring-stop charts: the uncut split, where each stop peaks, the size fit (`numbers.fit`), the relabels, the scale decision, the main pre-cut peaks, any long-trim pattern and, with `--scene` (the `scene` result's file), the camera view (`numbers.scene`). End with the **Open the report** line from [handing over local pages](../../references/local-pages.md).
6. **Compare.** To measure a change (new stops, a recalibration, a camera move), run `compare --dataset ID --from LOCAL --to LOCAL --vs-from LOCAL --vs-to LOCAL [--vs-dataset ID] [--calibration …] [--vs-calibration …] [--pair OLD=NEW,…] [--label TEXT] [--vs-label TEXT] --format text` with the window before the change first. Each window must sit inside one calibration (use `windows` to find the change). Pair renamed lines with `--pair` (the old 42.3 line became 40). Show the table and say what moved: the shares within ±0.25 and ±0.5, median offset, width, unmatched and No Cut, overall and per stop, and which stops have too few boards to judge. A better score means the boards sit more tightly on the posted sizes in the camera's own scale; it does not prove the sizes are right (see [reading the report](references/reading-the-report.md#the-size-fit-score)).
7. **Next steps.** Offer what the findings point to, without doing it. A camera view that moved between recordings points to the mount: readings shift with it until it is fixed, and stops calibrated before the move no longer sit where the boards stop. A large "longer than stop" uncut share means the saw line sits past the real blade, so thin trims post as No Cut. A relabel means two physical stops shared one line, or the line was renamed. Stops measuring well off their size need recalibration on the camera; calibrate-trimsaw-stops gives the values and steps when the user asks. This skill does not change camera settings; device setup and line editing happen on the camera or in Zira. Publish a report to share it only when the user asks (for example as a private claude.ai page in Claude Code); it holds customer readings.

To change the window, merges or factor, run `report` again (each run writes a new file). The page's range and interval controls work within the fetched weeks. Its Load button fetches more raw weeks, but those weeks have no derived columns, so build a new report for another window instead.

**Neighboring stops.** `check` and `report` return `neighbors` for original labels 0.5 or 1 length unit apart (for example 30/30.5 and 44/45). Reports add recorded cut/uncut counts and each bucket's share every five minutes, plus raw measured cut-length distributions for the same selected window. Original labels stay separate here even when relabels are merged elsewhere. Use From/To to inspect a production interval in both views together; rebuild to discover pairs outside the authored window. Report any `neighbors.omitted` coverage gap (the eight busiest pairs are shown). Explain observed counts and distributions from the report's tables or queries; do not infer which physical stop was active from its assigned bucket. Overlapping distributions and a small neighboring share are grounds to investigate possible spillover, not a measured error rate. An operator, production log or matching video must establish intended size. Keep sequential relabels and sparse samples distinct from simultaneous production. See [reading the report](references/reading-the-report.md#neighboring-stop-buckets).

Limits: one data source per report; readings only, so stop-line pixel positions and camera settings are not visible. The camera view sees only recordings uploaded to Zira and compares views, not lengths. The scale check assumes most uncut boards at a stop are already at that size. Pre-cut uses half-unit bins. Tables give per-row medians and percentiles, where a row can hold several boards; the summary numbers and histograms are weighted by boards. Exit codes: 0 done, 2 failed (the message explains), 3 incomplete fetch (say which weeks), 4 blocked (the JSON explains; a sign-in block means the user signs in again).
