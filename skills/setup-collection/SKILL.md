---
name: setup-collection
description: Connect a Modbus TCP meter (a power meter or a process sensor behind a Modbus TCP gateway) to an existing Zira data source — add the gateway or reuse one, connect the data source with its unit ID and a meter model or register maps, test-read it, switch it on — and later check whether it is collecting or end a gateway's waiting time after failures. Use for "connect the main power meter at 10.0.0.20 unit 1", "add another meter behind the C3 gateway", "is the compressor meter collecting", "why is the gateway failing" or "retry that gateway now". Creating the data source itself uses create-data-source (step 5, meters); the old collector's settings are read with show-data-sources (inventory collection).
---

Use the [local MCP tools](../../references/local-mcp.md) for the packaged commands below (tool `collection`). The command examples describe arguments; invoke the MCP tool instead of running them in a shell.

Read [authorized browsing](../../references/browsing.md) and [guided actions](../../references/actions.md). Run `node scripts/collection.mjs …` from this skill's directory with the same `--profile` throughout. Reads change nothing. Every write shows a preview first; after the user says yes, rerun the same command with `--apply`. It writes once and reads back; never repeat an `unverified` write.

**Words.** A *gateway* is what Zira's collector connects to: a Modbus TCP gateway with one or more meters behind it. A *binding* connects one Zira data source to a gateway through the meter's unit ID; with the user, call it the meter's connection. *Maps* say which register each metric of the data source is read from. A *network* is the secure link (VPN) between Zira and the site's own network.

**When not to use it.** The data source must exist first: create it with create-data-source (step 5, meters on shared metrics). Settings of the old collector are read-only with show-data-sources (`inventory` command `collection`); this skill does not change them.

**Who can do what.** Anyone who can see the site can read its gateways, status and meter models. Creating or changing a gateway or a meter's connection, a test read and ending a waiting time need a user who can edit the site (a site or company admin). For anyone else these stop with `authorization` and nothing changes: say that a site admin has to do this step.

1. **Formats first.** Always run `formats` before writing any connection, address or maps, and copy the shapes exactly: keys like `unit_id` and `word_order` are snake_case. The helper checks them before anything is sent.
2. **Scope.** Reuse the company and site. Find the data source (show-data-sources) and see what exists at the site: `gateways --company-id ID --site-id ID` and `status --company-id ID --site-id ID [--data-source-ids ID]`. Reuse an existing gateway for another meter behind the same gateway (the usual case: only the unit ID is new, and no network step is needed); a data source has only one binding.
3. **Gateway (only when the site has none for this meter).** `create-gateway --company-id ID --site-id ID --name "…" --protocol modbus_tcp --connection '{"host":"10.0.0.20","port":502}'` (polls every 60 s by default).
   - **Networks.** `gateways` lists the site's `networks`, and each gateway shows its `network`. A gateway at a private address (10.x, 172.16–31.x, 192.168.x) is reached only through the site's network (the VPN between Zira and the plant), and the network is requested and chosen in Zira, not here. When a result carries a `networkStep`, do not stop the work and do not send the user away empty-handed:
     1. Say in one or two plain sentences why (`why`) and what they do in Zira (`inZira`), and give the link as a clickable link: `meterUrl` when present (the meter's Collection tab), otherwise `networksUrl` (the site's Gateways & networks tab). Offer to open it in their browser.
     2. Meanwhile keep going with everything that does not need the network (`meanwhile`): create the gateway, the binding and its maps after the usual previews.
     3. Ask them to tell you when it is done. Then run `gateways` yourself: when the gateway shows a network, continue straight to the test read with what was already entered. Never ask them to repeat an address, unit ID or meter model.
     4. If the site has no network at all, the request is a one-time step with their IT and Zira and can take days. Say so, prepare what can be prepared, and tell them to come back with "continue the meter setup" once Zira confirms the network is active; then start again from `gateways`.
4. **Binding.** `create-binding … --endpoint-id ID --data-source-id ID --address '{"unit_id":1}'`. When the meter model is known, look for it with `profiles --protocol modbus_tcp --company-id ID` (and `profile --profile-id ID` for its maps) and add `--profile-id ID`: its maps are copied in, and `skippedMetricIds` lists metrics the data source does not have. A binding is always created off.
5. **Maps (without a meter model, or to fix one).** `set-maps … --binding-id ID --maps '[{"metricId":"1","source":{"table":"input","register":11,"type":"int32","word_order":"big"},"scale":0.001}]'`. It replaces all the binding's maps; the preview's `writableMetrics` from create-binding lists the metrics you can map. Never guess registers: use the meter's manual, a meter model or the user's values.
6. **Test read.** Ask the user first, every time it is a meter they have not approved in this conversation: it connects to their equipment, but saves nothing. `test-read … --binding-id ID`. Show each metric's raw and saved value; a value way off usually means a wrong scale, type or word order. If the read fails and the result has a `networkStep`, follow the Networks steps above instead of changing the meter's settings.
7. **Switch on.** `update-binding … --binding-id ID --enable` (and `update-gateway … --endpoint-id ID --enable` if the gateway is off). Check `status` a few minutes later.
8. **Reading status.** Each binding has a `health`: `ok` (the last poll saved a reading; see `lastOkAt`), `failing` (`lastError` says why), `not-polled-yet`, `off`, or `data-source-deleted`. `gatewayRun` is the gateway's last run: `failuresInARow`, `lastError` and `nextTryAt`. Never say a meter is collecting until `status` shows `ok` with a recent `lastOkAt`; on or saved is not collecting.
9. **A gateway that keeps failing.** After failures the collector waits longer each time, up to 15 minutes between tries (`gatewayRun.waiting`). Find and fix the cause first (address, a `networkStep`, unit ID), confirm with a test read, then `release … --endpoint-id ID`: the preview shows the failures and the next try; with `--apply` the collector tries again within a minute. `not-needed` means it is not waiting.

**Stops.** On `blocked`, say what it means in plain words and that nothing was changed: `duplicate` (that name or data source already has one: reuse it), `scope` (not at this site), `refused` (Zira refused it: show `details`), `authorization` (this user cannot change this site: a site admin can), `unavailable` (this build does not set that up: Zira does), `not_found`. If `release` stops with `not_deployed` (or `not_found`), that part of Zira is not available yet: say so and do not retry. Deleting a gateway or a meter's connection is done in Zira, not here.
