---
name: build-dashboard
description: Build or update a Zira dashboard with native charts, KPIs, tables, filters and AI summary widgets grounded in real source metrics, then verify saved settings and results. Use for new dashboards or requested widget changes; use show-dashboards to find existing dashboards and duplicate-dashboard to copy one.
---

Read [authorized browsing](../../references/browsing.md) and [guided actions](../../references/actions.md). Run helpers relative to this skill directory with the same `--profile`. Author the widgets here in Codex or Claude; the web AI builder is optional, not the required last step.

Honor a requested transport. The commands below use the plugin's internal-API client, not MCP.
For an explicit MCP request, discover connected Zira write tools and follow their actual schemas;
if unavailable, retain the draft and report the gap instead of switching to browser editing.

1. **Understand the decision.** Reuse the site, sources and purpose supplied. Ask only for a missing decision that changes the result: what users need to learn or act on, comparison/baseline, time window, or denominator. Turn the request into questions, then a short widget plan (question → metric/formula → visual → expected check). Suggestions are starting points, never the limits of the dashboard. Prefer native widgets over embeds when native calculations can answer the question.
2. **Ground the plan.** Discover sources with `node ../../scripts/browse.mjs devices --company-id ID --site-id ID`. Inspect metrics and a bounded sample using readings-report's `sources --metrics`, `fetch` and `query` when necessary; don't guess metric IDs, units, enum values, weighting or missing-data meaning. Explain unavailable data before substituting an approximation. For an existing dashboard, run `node ../../scripts/dashboard-widgets.mjs context --company-id ID --site-id ID --dashboard-id ID --out CONTEXT.json` and preserve unrelated widgets and settings.
3. **Create the container when needed.** Preview `node ../../scripts/dashboards.mjs create --company-id ID --site-id ID --name "…" --description "…" --data-source-ids ID,ID --range last-7-days --interval hourly --profile prod`. Choose range and interval for the actual question (`help` lists options). On `nameTaken`, reuse the selected dashboard or choose a distinct name. Apply the reviewed creation with `--apply` when authorized. Share its `url`, then run `dashboard-widgets.mjs context` for the created ID. An empty container is not a completed dashboard.
4. **Author custom widgets.** Read [native settings and payloads](references/native-widgets.md), and [analysis patterns](references/analysis-patterns.md) for formulas, weighted data and trimsaw reports. Write a JSON spec outside the plugin directory, using the context's actual metrics. Design the layout as a readable narrative: summary, explanation, comparison and inspectable detail. Use shared filters only when they help. For non-analytical families, consult [other widget settings](references/other-widgets.md); do not claim the helper supports a family it does not yet implement.
5. **Preview, save, verify.** Run `node ../../scripts/dashboard-widgets.mjs save --company-id ID --site-id ID --dashboard-id ID --spec SPEC.json --profile prod`. It validates the whole batch and returns exact payloads, all four layouts, and `revision`. Explain what will change and any approximation. Reuse the user's explicit authorization; otherwise obtain approval for that concrete plan. Run the same command with `--apply --expected REVISION`. Creation precedes dependent filter widgets. The helper has no delete route. It checks scope, stale previews, receipts, and read-back; a partial/unknown attempt stops without replay. On authorization denial, report the blocked route and retain the draft; follow web continuation, never use a different credential source to bypass it.
6. **Review the result, not just the response.** Open the returned dashboard URL in the host browser. Verify every widget renders, populated metrics have data, categories/legends/units make sense, filters affect their intended widgets, and desktop/mobile layouts are readable. Compare key totals, shares, weighted means and at least one distribution with independent raw-reading queries for the **same site-time range and filters**. Check a zero/empty range and a narrower populated range. A saved configuration is not evidence of a correct chart. Repair only authorized widgets after a fresh context/preview; preserve existing series IDs and untouched settings. Report verified behavior and remaining gaps honestly.

Use `dataResearch` for KPI, grouped KPI, KPI table, column, bar, pie and time series; `derivedMetrics` for row calculations and category bins; `customAgg` for formulas after grouping. `header`, `filter` and read-only `readings` are also supported. For an AI summary/AI Insights request, read [AI summary settings and payload](references/ai-summary.md) and use `aiSummary`; it saves a question and explicit source-widget references, not a static answer. Referenced draft analytics are saved before the summary. Production backend admission supports type 18; verify availability in other environments. Don't replace an unsupported statistic (for example weighted percentiles) with a similarly named but different metric. There is no arbitrary JavaScript/HTML widget injection or scheduled-report creation in this flow.

Deliver the dashboard link, the questions it answers, the chosen time basis, and the validation result. State if only the container/draft exists or the browser/data checks remain blocked. Schedule summaries only when requested, using schedule-ai-report.
