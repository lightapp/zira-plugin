---
name: evaluate-model
description: Evaluate a Zira vision model — see how accurately it detects each class (precision, recall, the images it gets wrong, drawn on the images) by running it on a dataset on this computer. Works from a Zira camera's models and dataset versions, from a Pallet Vision camera's recent QA sessions (frames the model never trained on, sliced like Zira's training datasets), or from files on this computer (supported model files and dataset ZIPs). Use for "evaluate model", "test my model", "how accurate is my model", "evaluate the newest model on raised-nailes-new for Cam 1 Quality", "test the nails model on the latest validation session", or "check this .tflite on that dataset"; not for opening a dataset to annotate (open-dataset) or device health.
---

Check [build restrictions and prerequisites](../../references/distribution.md) first. Public builds support `.tflite` models only; do not offer `.pt` setup or execution even if another local environment has PyTorch installed.


Read [authorized browsing](../../references/browsing.md) (including "Asking the user to choose") and [guided actions](../../references/actions.md). Run `node ../../scripts/datasets.mjs …`, `node scripts/evaluate.mjs …` and `node scripts/sessions.mjs …` from this skill's directory with the same `--profile`. Nothing is uploaded or changed in Zira.

**When the request is open-ended** ("evaluate model", "test my model"), start with one line on what this does: "I'll run a model on a dataset on this computer — fast, nothing uploaded — and show precision and recall per class with every image's boxes." Then ask only what is missing, using the choice UI.

**Show, then work.** Whenever a camera is known, open its Models tab with the host's browser tool before slower steps and say what comes next.

1. **Where are the model and dataset?** Skip this when the request already says (a camera, a dataset name, validation or QA sessions, or file paths). Otherwise ask: *From a Zira camera* (recommended) / *Recent QA sessions* (Pallet Vision: frames the model never trained on) / *Files on this computer*. A mix works too (a Zira model on a local dataset, or the reverse).
2. **Zira camera.**
   - Run `datasets.mjs scope`. One site → its name is `chosen.place`. A few → ask its site `question`. Many → ask its camera `question` (recent cameras; a picked camera's `value` is its device ID) or its `ask` text.
   - Then `datasets.mjs find --place SITE [--source CAMERA]`: one camera → use it; several → ask its `question`. Open the camera's Models tab now.
   - `datasets.mjs datasets --device-id ID` → ask the dataset `question`; then `datasets --device-id ID --dataset NAME` → its `modelQuestion` (models trained on this dataset first) unless the user named one ("newest" = the newest model). Use the newest version unless asked (`versionQuestion`).
   - `datasets.mjs open --device-id ID --view evaluate --dataset NAME --version VID --model MID`: if `compatibility.sameClasses` is false, show both class lists and ask: pick another model, or continue scoring only the matching classes (`--allow-class-mismatch`). Mention `recorded` training-time metrics with their `note` (not a fresh run).
   - Say: "I'll download the version (N MB) and the model (M MB) from Zira and run it on this computer — that's fastest and nothing is uploaded." Then `evaluate.mjs fetch --device-id ID --file-id VID` and `--file-id MID` (cached after the first time). If `download_not_enabled`, guide the one Download click from `manual` and use `find-download`.
3. **Recent QA sessions** (Pallet Vision). A model trained on a dataset scores well on its images, so fresh session frames give a fairer picture.
   - Find the camera as in step 2 and fetch the model (`evaluate.mjs fetch --file-id MID`).
   - `sessions.mjs list --device-id ID` → ask its `question` (latest session, the one before, or recent days).
   - `sessions.mjs fetch --device-id ID --session DAY::SESSION …`. With `needsConfirmation`, say how many frames and MB and ask; offer `--frames N` (each session's newest N) for a quick look, then rerun with `--confirm`.
   - `sessions.mjs prepare --device-id ID --session … --classes-from MODEL_PATH` builds the input this model needs (nail intersection slices, geometry or pallet images) exactly as Zira's "Generate training datasets" does, with the model's classes. Then run step 6 on the `next` dataset with `--split test`.
   - `sessions_unavailable`: this Zira environment does not offer session downloads to the plugin yet. Say so, give `pageUrl` (the Validation tab) and offer a dataset version instead.
   - Labels are the reviewer's correction where someone fixed a frame, otherwise the device's own output. Report `reference.summaryBySource` separately: on device-labelled images precision and recall measure agreement with the model running on the device, not accuracy; reviewer-corrected images are true scores. To compare two models, evaluate both on the same prepared sessions (prepare once per model when their classes differ).
4. **Files on this computer.** If the user attached or dropped the files in chat, use their paths. Otherwise run `evaluate.mjs local-files` and ask its `datasetQuestion` and `modelQuestion` (the two newest matching files in Downloads plus **Choose a file…**). For Choose a file…, run `evaluate.mjs choose --kind dataset|folder|model`: it opens the system file dialog in Downloads and returns the `path` (`chosen: false` means they closed it — ask again or accept a typed path). A dataset can be a ZIP or a folder with `data.yaml`. Then `evaluate.mjs inspect --dataset PATH --model PATH`: report classes and images per split. A `.tflite` carries no class names: if `sameClassCount` is true without `sameClasses`, ask whether its classes follow the dataset's order, or for its class names (`--model-classes a,b,c`).
5. **Runtime, once:** `evaluate.mjs status` (instant). If not ready, ask once: "Set up model evaluation on this computer? It downloads about 30 MB of Python packages (PyTorch for .pt models is much larger)." Then `evaluate.mjs setup` (internal builds only: `--with-pt` for .pt).
6. **Run:** `evaluate.mjs run --dataset ZIP_OR_DIR --model FILE --split val [--model-classes …] [--allow-class-mismatch]` (`--limit 20` for a quick look on big datasets).
7. **Show the results visually:** `evaluate.mjs open --report <reportHtml>` right away, and end the answer with the **Open the evaluation** line from [handing over local pages](../../references/local-pages.md) (default browser; the in-app browser shows local files only as a static snapshot). The report has headline numbers, a per-class table and every image with labels and predictions drawn (green correct, red missed, orange extra, with class and score), errors first, with filters. Each class has its own confidence and match IoU in the table, and changing them re-scores the numbers and images live; the page address keeps the choice, so a link reopens the same view.
8. **Then answer briefly in chat:** overall precision/recall/F1, a per-class table (`comparable: false` → "not comparable: the model has `modelClass` there"), `confusions` when present (labeled objects found at the right place under another class, such as nails predicted as knots), the main finding in one or two sentences, `classWarning`, `modelMs` with its `timingNote` (this computer, not the device), and that scores depend on `preprocessing` (TFLite stretch vs PT letterbox). Point to the open report for the images; give the JSON path only if a developer asks. Offer next steps as a choice: another split or all images, another model, or per-class confidence and match IoU (set in the report's class table).

Say "evaluated" only after `run` returned `complete: true`; a cancelled run is partial. Recorded training metrics are not an evaluation. If a step fails, say what is ready and what is still needed.
